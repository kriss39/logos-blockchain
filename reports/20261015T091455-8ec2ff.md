### Missing-requirement (missing capability)

#### Finding 2 (F-d4270761) — recommended inscription framing has no implementation anywhere in the unit — **disputed**, low severity, medium confidence

The template lists as an objective "Provide a standard message format while allowing flexibility for custom implementations" and specifies a recommended binary framing for inscriptions (MessageCount byte; per-destination 32-byte ChannelId and total-length field; per-message length-prefixed payloads), noting that following it "ensures better interoperability with other channels in the ecosystem". The zone SDK offers no encoder, decoder, or type for this framing: `Inscription` is an unchecked byte vector, `ZoneBlock::data` is documented as "The opaque inscription data", and `channel_inscriptions` hands payloads back unparsed with no destination-based demultiplexing. Every zone wanting the ecosystem-standard format must hand-roll it. The finding does not establish a violation of a "must": the spec marks the format as recommended, not enforced, so this is a gap against a "should". Prose-adjacent capability gap; no failing unit test exists to write, so the proof is a command showing the absence.

- Locations: `zone-sdk/src/lib.rs:135-140` (`ZoneBlock { data: Inscription }`, opaque), `zone-sdk/src/sequencer/block_fetch.rs:494-514` (`channel_inscriptions` returns raw payloads).
- Repro: `sh test/2/no_recommended_message_format_impl.sh` → observed: the grep over zone-sdk/src and core/src/mantle for `message_count`/`MessageCount`/`message_length`/"recommended format" reports no candidate codec identifiers.
- Second pass: rejected — ran the script successfully and independently read lib.rs:135-140, channel_inscriptions and inscription validation; the specification says "This structure is not enforced by the blockchain. It serves as a recommended standard for interoperability" and explicitly permits channels to "Implement their own custom message formats based on specific requirements". It provides the recommended standard in the document itself and never requires an SDK codec or destination demultiplexer; opaque bytes support the expressly allowed custom-implementation path, and identifier search alone cannot prove an implementation is absent.
- Disposition: both passes agree the SDK ships no codec for the recommended framing and that the chain correctly treats inscriptions as opaque. In dispute is whether the Objectives sentence "Provide a standard message format" obliges the implementation (first pass) or is discharged by the format's definition in the document itself, given the explicit custom-format allowance (second pass).
- Fix: if the objective is read as the first pass does, add a `zone_sdk::message_format` codec (encode/decode of the recommended framing, enforcing MessageCount ≤ 255 and the corrected length-prefix widths per finding 1) with round-trip and truncated-frame tests; those tests fail to compile today because the API is absent. Otherwise no change is needed.

### Spec-drift (documentation and attestation drift)

#### Finding 1 (F-242437da) — Message Format grammar says `ChannelId = 4 *Byte`; prose and implementation are 32 bytes — **disputed**, low severity, high confidence

The template's Message Format grammar defines `Destination = ChannelId` / `ChannelId = 4 *Byte`, a 4-byte destination identifier. The implementation's ChannelId is a 32-byte newtype (`pub struct ChannelId([u8; 32])`, core/src/mantle/ops/channel/mod.rs:24) used as the channel key throughout the unit, and the same spec section's prose agrees with the code ("Destination: A 32-byte number identifying the target channel"). Neighbouring grammar lines also contradict their prose (`MessageLength = UINT64` vs "4-byte unsigned integer"; `Message = UINT32 *Byte` vs "3-byte length field"). A third party building the recommended format from the grammar frames destinations and lengths incompatibly with one built from the prose or the Rust types. The finding does not establish a code defect: both passes hold the code right for the current intent and the document the thing to fix; the proof test exists to document the divergence, not to demand a 4-byte ChannelId.

- Locations: `core/src/mantle/channel.rs:104` (`channels: HashTrieMapSync<ChannelId, ChannelState>`), `zone-sdk/src/lib.rs:101` (re-export for Node implementors).
- Repro: `cargo test --locked -p logos-blockchain-core --test bork_20261015T091455_8ec2ff_1` → observed: ``assertion `left == right` failed: Message Format grammar says `ChannelId = 4 *Byte`; the implementation encodes a ChannelId as 32 bytes (matching the section's prose, which says 32 bytes) — left: 32, right: 4`` (exit non-zero).
- Second pass: rejected — independently read ops/channel/mod.rs:23-25 and block_fetch.rs:494-514; the specification explicitly says "Destination: A 32-byte number identifying the target channel" and "This structure is not enforced by the blockchain", so the grammar conflicts with its own prose but does not establish a mandatory 4-byte core channel identity. The proposed test asserts one inconsistent, optional grammar interpretation against the core identifier, not an enforced requirement; it declined to run the test because the asserted requirement is invalid regardless of its result. It verified the ref: 0.3.0 resolves to 1da2d9d69a80452cf6b5d0e68304762d510c8a6c, proof HEAD is aa6570e2e436112ac7e35ca09ecb5434f2caf738, and the diff between them over all unit paths is empty.
- Disposition: both passes agree the LIP's grammar contradicts its own prose and the implementation, and that a documentation correction to the LIP is warranted. In dispute is only the classification — whether an internally inconsistent, optional grammar constitutes spec-drift against the implementation (first pass) or is a pure document defect establishing no divergence of this codebase (second pass).
- Fix: correct the LIP document, not the code — change the grammar to `ChannelId = 32 *Byte`, reconcile `MessageLength` (UINT64 vs "4-byte unsigned integer") and the per-message length prefix (UINT32 vs "3-byte length field") so grammar and prose agree.

#### Finding 3 (F-6bc21351) — `DepositInfo` documented as "observed in a finalized L1 block" but delivered non-finalized via `Event::BlocksProcessed::deposits` — **disputed**, low severity, medium confidence

The template requires that asynchronous operations handle finality periods correctly and that a destination processes an observed message only once it has achieved finality (or a chosen threshold). zone-sdk documents `DepositInfo` as "A channel deposit observed in a finalized L1 block" (types.rs:680-683), yet the one event surface that delivers it outside the finalized stream — `Event::BlocksProcessed::deposits` — documents the opposite: "Surfaced non-finalized so a consumer can pin a deposit without waiting for finalization" (types.rs:415-425). The same type travels a finalized path (`FinalizedOp::Deposit`) and a non-finalized one, and its own doc claims only the former; a consumer trusting the struct doc (e.g. a bridge minting L2 tokens against an L1 deposit, the correlation adapter.rs:387 describes against finalized deposits) can act on a deposit later reorged out. The finding does not establish fund loss or any in-unit misbehaviour: the delivery split is intentional and pin-deposit is safe by construction; the defect claimed is the stale struct-level doc contract.

- Locations: `zone-sdk/src/sequencer/types.rs:680-683` (stale `DepositInfo` doc), `zone-sdk/src/sequencer/types.rs:415-426` ("Surfaced non-finalized" field doc), `zone-sdk/src/sequencer/block_fetch.rs:56-60` (`BlockEventResult::deposits` from live blocks).
- Repro: `sh test/3/depositinfo_finality_doc_contradiction.sh` → observed: the script prints both contracts from the tree — types.rs:680 "A channel deposit observed in a finalized L1 block" against types.rs:417 "Surfaced non-finalized so a consumer can pin a".
- Second pass: rejected — ran the script successfully and independently traced both delivery paths (live deposits via block_fetch.rs:178-218; finalized via node.immutable_blocks and backfill.rs:140 onward). It agreed there is a real API documentation inconsistency worth fixing, but held that the script proves only that inconsistency, not divergence from this template: the event-field doc explicitly says "Surfaced non-finalized" and instructs branch reconciliation, `PinDepositInfo` is safe by construction (the pin's transfer consumes the deposited note), and no code in the unit processes a live deposit as finalized; the claimed unsafe mint requires a consumer that ignores the explicit field contract, and no such consumer is reproduced.
- Disposition: both passes agree the `DepositInfo` doc at types.rs:680 is stale, the event field is explicitly non-finalized, and the SDK's own behaviour keeps finalized and live views separate. In dispute is whether a stale struct-level doc that invites a finality mistake counts as drift against the template's finality requirement (first pass) or as an API-documentation defect outside the template's scope because no in-unit code violates the finality rule (second pass).
- Fix: correct the doc contract — on `DepositInfo` replace "observed in a finalized L1 block" with wording naming both delivery paths and their guarantees, disambiguate the crate-root `Deposit` doc (lib.rs:142), and optionally encode the finalized/non-finalized distinction in the type system so a consumer cannot confuse the two paths.

No findings were raised in the contradicts-spec, wrong-default, off-by-requirement or undefined-behaviour classes.
