### contradicts-spec (proven violations)

#### Finding 1 (F-f160eb87) — ChannelMultiSigProof encodes each IndexedSignature signature-first, the reverse of the spec's `IndexedSignature = SignerIndex Ed25519Signature` — **confirmed**, medium severity, high confidence

Spec revision 1.9.0 (2026-10-01, "Swap Ed25519Signature and SignerIndex order in IndexedSignature") fixes each element of a ChannelMultiSigProof as `IndexedSignature = SignerIndex Ed25519Signature` with `SignerIndex = UINT16`: the 2-byte little-endian index of the signing key first, then the 64-byte signature. ChannelConfigOpProof, ChannelWithdrawOpProof and ChannelTransferOpProof are all this ChannelMultiSigProof.

The code lays it out the other way round. `IndexedSignature` derives `BinaryCodec`, which concatenates fields in declaration order, and declares `signature: Ed25519Signature` before `channel_key_index: u16`. The unit's proof codec (`OpProof::ChannelMultiSigProof`, encoded through `op_proof.rs:50-58` and decoded through `OpProof::decode_for_op`) therefore writes `SignatureCount | Ed25519Signature | SignerIndex` for each entry, and reads spec-encoded bytes misaligned: the signer index becomes the first two bytes of the signature, and the index is taken from the last two signature bytes. The code at this tag (committed 2026-09-30) predates the 1.9.0 swap; the pinned fixture `CHANNEL_MULTI_SIG_HEX` and the size comment at `channel_multi_sig_proof.rs:180` pin the old order. A spec-conformant wallet or node and this node cannot exchange any channel multisig proof that has a signature.

What the finding does not establish: no fund loss or consensus split is shown; the transaction hash and op ids are unaffected because proofs are not hashed, and the proof size is unchanged (66 bytes per signature either way). Scope: SignedMantleTx encode/decode in `logos-blockchain-core` (mempool and block bodies), every ChannelConfig, ChannelWithdraw and ChannelTransfer proof with at least one signature; a channel-creating ChannelConfig with an empty proof is unaffected. The root-cause line is outside the brief's file list but is reached through the unit's `op_proof.rs`; the generic derive behaves as documented and is not at fault.

- Locations: `core/src/mantle/ops/op_proof.rs:22` (the `ChannelMultiSigProof` variant the unit encodes and decodes), `core/src/proofs/channel_multi_sig_proof.rs:12-17` (`IndexedSignature` field order: `signature` then `channel_key_index`), `core/src/proofs/channel_multi_sig_proof.rs:179-182` (size comment pinning the old order), `core/src/mantle/fixtures/proofs/proof_values.rs:40` (`CHANNEL_MULTI_SIG_HEX` fixture pinning the old order).
- Repro: `cargo test --locked -p logos-blockchain-core --all-features --test 20261023T070011-08cb0f-1` (artifact `core/tests/20261023T070011-08cb0f-1.rs`, expect: nonzero) → observed: 2 failed. `signed_tx_encodes_the_signer_index_before_the_signature`: "assertion `left == right` failed: IndexedSignature = SignerIndex Ed25519Signature: the UINT16 signer index must precede the 64-byte signature", left `...0100abab...abab0201` (signature, then index), right `...01000201abab...abab` (index, then signature). `signed_tx_decodes_the_signer_index_before_the_signature`: "the first two bytes are the signer index", left 43947 (0xABAB, the last two signature bytes), right 258 (0x0102). Counter-check by the first pass: with the two field declarations swapped as a reverted local edit, both tests pass.
- Second pass: confirmed — "Audited annotated tag object 1da2d9d69a80452cf6b5d0e68304762d510c8a6c (0.3.0) peels to resolved commit f76be2dde171711299eb9c25ec7cc6a3821fe240; proof-branch HEAD is 62385cb61c86d6f8206e4cdfb0088f99a87ffe99, adding only the three proof files. Encoding ends in signature bytes then 0201; spec requires 0201 then signature bytes. Decoding spec bytes yields index 43947 instead of 258. - Fix: declare `channel_key_index: ChannelKeyIndex` before `signature: Ed25519Signature` in `IndexedSignature` (`core/src/proofs/channel_multi_sig_proof.rs:12-17`) so the derived codec writes `SignerIndex Ed25519Signature`; `Ord` (index, then signature) can stay as is. Coordinate the byte change with other implementations and wallets. `core/tests/20261023T070011-08cb0f-1.rs` fails before the fix and passes after it.

#### Finding 2 (F-9c2a31b4) — ClaimPowReward is paired with a zero-byte NoOpProof, an OpProof alternative the spec does not define, instead of the 128-byte ZkSigProof the spec assigns it — **confirmed**, medium severity, high confidence

Spec revision 1.8.0 (2026-09-08) adds the ClaimPowReward payload and states that "its proof is a `ZkSigProof`". The Op Proofs section requires one OpProof per Op with `type(OpProofs[i]) == ProofFor(Op[i])`, lists seven proof productions (none of them empty), and defines `ZkSigProof = ZkSignature = Groth16 = 128BYTE`.

The code gives `ClaimPowRewardOp` `type Proof = NoOpProof`. That proof encodes to zero bytes and decodes by consuming nothing, and it is carried in an extra `OpProof::None(NoOpProof)` variant that is not among the spec's OpProof alternatives. As a result the unit's proof decoder (`OpProof::decode_for_op`) reads no proof bytes for a ClaimPowReward; `SignedOps::from_parts` rejects a ZkSig proof for it with `OpProofMismatch`; and the unit's signed-size predictor hard-codes `OpRef::ClaimPowReward(_) => 0, // no proof`, so storage gas is priced on a size 128 bytes short of the spec layout. A spec-encoded signed transaction with a ClaimPowReward is mis-parsed: when the ClaimPowReward is last, its 128 proof bytes are left over and `decode_all` and the serde path reject the transaction for trailing bytes; when it comes before another op, that op's proof is read from the ClaimPowReward's ZkSigProof bytes. In the other direction, transactions this code encodes lack the 128 bytes a spec decoder expects.

The code has used NoOpProof since the op was introduced (2026-08-07), before the spec revision. The spec is the authority, so this is filed as contradicts-spec; if the no-proof design is intentional, the LIP must be amended instead. What the finding does not establish: verifying the ClaimPowReward proof belongs to the Mantle spec and is out of this document's scope; the tx hash is unaffected because proofs are not hashed. Scope: SignedMantleTx proof column encode/decode and the signed-size prediction used for storage gas in `logos-blockchain-core`; deterministic for every signed transaction containing a ClaimPowReward. `pow.rs` is outside the brief's file list; `op_proof.rs:23,45` and `codec.rs:61` are in the unit.

- Locations: `core/src/mantle/ops/op_proof.rs:45` (decode dispatch reads a NoOpProof for ClaimPowReward), `core/src/mantle/ops/op_proof.rs:23` (the extra `OpProof::None(NoOpProof)` variant), `core/src/mantle/transactions/codec.rs:61` (`=> 0, // no proof` in the size predictor), `core/src/mantle/ops/pow.rs:285-288` (`type Proof = NoOpProof`), `core/src/mantle/ops/op.rs:285` (`does_proof_match` pins the NoOp pairing).
- Repro: `cargo test --locked -p logos-blockchain-core --all-features --test 20261023T070011-08cb0f-2` (artifact `core/tests/20261023T070011-08cb0f-2.rs`, expect: nonzero) → observed: 3 failed. `signed_tx_decodes_the_zk_sig_proof_of_a_claim_pow_reward`: decoding `MantleTx([ClaimPowReward]) || 0x5A x 128` fails with "type(OpProofs[i]) == ProofFor(ClaimPowReward) == ZkSigProof: its 128 bytes must be read as the operation's proof, not left undecoded; left: 128, right: 0". `signed_tx_pairs_a_claim_pow_reward_with_a_zk_sig_proof`: `SignedOps::from_parts(ops, [OpProof::ZkSig(..)])` gives "rejected with: Some(OpProofMismatch { index: 0, ... actual_proof: ZkSig(...) })". `predicted_signed_size_counts_the_zk_sig_proof_of_a_claim_pow_reward`: `minimum_signed_transaction_size` gives left: 98, right: 226. Counter-check by the first pass: `type Proof = ZkSignature` in `pow.rs` plus one fixture line (reverted) makes the decode and pairing tests pass; the size test keeps failing until `codec.rs:61` also counts `COMPRESSED_PROOF_SIZE`.
- Second pass: confirmed — "Independently ran cargo test --locked -p logos-blockchain-core --all-features --test 20261023T070011-08cb0f-2: all three tests failed for the claimed reasons. The decoder leaves all 128 appended proof bytes, pairing with ZkSig returns OpProofMismatch, and the size predictor gives 98 rather than 226. - Fix: make ClaimPowReward's proof a ZkSigProof: set `type Proof = ZkSignature` in `impl ProvableOperation for ClaimPowRewardOp` (`core/src/mantle/ops/pow.rs:285-288`); count `COMPRESSED_PROOF_SIZE` for `OpRef::ClaimPowReward` in `minimum_signed_transaction_size` (`core/src/mantle/transactions/codec.rs:61`), grouped with the other ZkSigProof ops; remove `OpProof::None` / `OpProofRef::None` / `NoOpProof` if nothing else uses them; verify the signature in preverify/verify following the Mantle spec (presumably by `public_key` over the tx hash, as for Transfer); update `does_proof_match` (`op.rs:285`), the SignedOps fixture (`fixtures/transactions/tx_list/signed_ops.rs:91-106,126`: append `ZK_SIG_HEX` and use a ZkSignature) and the gas/size expectations. If the protocol intentionally needs no proof, amend the LIP (the 1.8.0 text and the OpProof list) instead. `core/tests/20261023T070011-08cb0f-2.rs` fails before the fix and passes after it.

#### Finding 3 (F-09095f5f) — SDPActive's Metadata is encoded as a bare 1-byte type tag plus the activity proof, with no UINT32 length prefix, although the spec defines `Metadata = UINT32 *BYTE` — **confirmed**, medium severity, high confidence

The spec defines `SDPActive = DeclarationId Nonce Metadata` with `Metadata = UINT32 *BYTE ; Service-specific node activeness metadata`, and its overview says lists are length-prefixed with fixed-width uints.

The code derives the encoding of `ActiveMessage` (= `SDPActiveOp`) as `declaration_id | nonce | ActivityMetadata`. `ActivityMetadata`'s hand-written codec writes a 1-byte type tag (0x01 = Blend) and then the `ActivityProof` bytes directly; there is no UINT32 length. So the unit's operation codec (`Op::encode` via `op_ref.rs:150`, `Op::decode` at `op.rs:148-150`) emits four bytes after Nonce that are not a length (`01 0a 00 00` for the sample) and rejects a spec-encoded SDPActive, because it takes the first byte of the UINT32 length as the metadata type tag (`UnknownDiscriminant`). The comment at `sdp/mod.rs:596` ("plain field-order concat") claims conformance. SDPActive bytes are part of `MantleTx`, so the divergence also changes the tx hash preimage (`MANTLE_TXHASH_V1 || MantleTx`) of every transaction that carries an SDPActive: signatures made over a spec-computed tx hash do not verify here, and the reverse. The encoder before 2026-06 did write the UINT32 length (`decode_sdp_active`, commented "Metadata = UINT32 *BYTE"); commit `cee30f6c` ("migrate SDPActiveOp to NomEncode/Decode") removed it, and every spec revision since keeps UINT32. This is a regression against the spec, not spec drift.

What the finding does not establish: the inner, service-specific metadata layout is not laid out by this LIP, so only the missing outer UINT32 length is asserted; the second pass notes the supplied spec does not independently define the hash preimage, so the hash consequence is a downstream effect of the encoding divergence, not a separate hash requirement. Scope: Op/MantleTx encode and decode in `logos-blockchain-core` and therefore the tx hash preimage and signatures of every transaction carrying an SDPActive (the per-epoch activity message of SDP providers); other operations are unaffected. The root-cause lines are in `core/src/sdp/mod.rs`, outside the brief's file list, reached through the unit's Op codec.

- Locations: `core/src/mantle/ops/op.rs:148-150` (the unit's decode dispatch for SDPActive), `core/src/sdp/mod.rs:596-602` (`ActiveMessage` derived codec and the conformance comment), `core/src/sdp/mod.rs:629-664` (`ActivityMetadata` codec: tag then proof, no length), `core/src/mantle/fixtures/ops/sdp.rs:47-63` (pinned fixture with the unprefixed layout).
- Repro: `cargo test --locked -p logos-blockchain-core --all-features --test 20261023T070011-08cb0f-3` (artifact `core/tests/20261023T070011-08cb0f-3.rs`, expect: nonzero) → observed: 2 failed. `sdp_active_metadata_is_prefixed_with_its_uint32_length` (encoding `ActiveMessage::sample()`): "assertion `left == right` failed: Metadata = UINT32 *BYTE: the four bytes after Nonce must be the little-endian count of the metadata bytes that follow; encoded Metadata field: 010a0000008a88e3dd...; left: 2561, right: 225". `sdp_active_decodes_a_uint32_length_prefixed_metadata` (decoding opcode | DeclarationId | Nonce | `e5000000` | 229 metadata bytes): "an SDPActive whose metadata is behind its UINT32 length must decode, got Err(UnknownDiscriminant { type_name: \"logos_blockchain_core::sdp::ActivityMetadata\", discriminant: 229 })". The decode test takes the inner metadata bytes from the code's own `ActivityMetadata` codec and wraps them in the UINT32 length unless that codec already writes one, so it holds whichever codec a fix adds the length to. Counter-check by the first pass: with `ActivityMetadata`'s codec writing and reading a UINT32 length before the tag (reverted local edit), both tests pass.
- Second pass: confirmed — "Independently ran cargo test --locked -p logos-blockchain-core --all-features --test 20261023T070011-08cb0f-3: both tests failed. The first four metadata bytes parse as length 2561 although only 225 bytes follow; adding the required length causes UnknownDiscriminant 229. Independently read ActiveMessage and ActivityMetadata codecs in core/src/sdp/mod.rs: the derived outer codec concatenates declaration_id, nonce, metadata; metadata writes u8 tag 1 followed directly by ActivityProof, and decoding reads that tag immediately. There is no UINT32 metadata length on this operation path. This contradicts SDPActive = DeclarationId Nonce Metadata and Metadata = UINT32 *BYTE. The supplied spec does not independently define the hash preimage; confirmation concerns the concrete encoding divergence, not an additional hash-algorithm requirement."
- Fix: encode SDPActive's metadata as `UINT32 length || metadata bytes`. Either give `ActiveMessage` a hand-written codec that wraps `ActivityMetadata` in a u32 length, or add the length inside `ActivityMetadata`'s codec (`sdp/mod.rs:629-664`). On decode, read the u32, take exactly that many bytes, decode the `ActivityMetadata` from them, and reject leftovers; bound the length, as the old `MAX_ENCODE_DECODE_METADATA_SIZE` did, to avoid over-reads. Then update `encoded_length`, the pinned fixtures (`core/src/mantle/fixtures/ops/sdp.rs:47-90` and the all-ops vectors, `ALL_OPS_COLUMN_HEX`), fix the comment at `sdp/mod.rs:596`, and regenerate the tx-hash test vectors (`ops/mod.rs` `mantle_test_vectors`), since SDPActive tx hashes change. `core/tests/20261023T070011-08cb0f-3.rs` fails before the fix and passes after it.
