## How the evidence is classed

- **Proven violations** (the code does something the specification forbids, demonstrated by a failing test): findings 1 (trailing inscription bytes accepted), 2 (genesis outputs not validated), 5 (empty chain id rejected), 8 (epoch reward copied, not derived), 10 (ceremony accepts fewer than three entropy sources), and 3 (the ceremony tool panics on the block hashes the spec names as its inputs; the spec is silent on the bytes-to-field mapping, so the class is undefined-behaviour rather than contradicts-spec).
- **Missing capabilities** (the tree lacks something the specification requires): finding 7 (no check of the genesis declaration count against Blend's minimum network size, unconfirmed because the second pass reads the clause as conditional), and the pool-seed half of finding 8 (no maximum-supply constant exists, so POW_REWARD_POOL_GENESIS = 5/1000 of maximum supply cannot be checked).
- **Documentation and attestation drift** (the specification contradicts what the code deliberately does, and the document is the likelier side to correct): findings 4 (faucet notes excluded from D), 6 (nonce must be a canonical BN254 scalar; the spec's own example does not decode), 9 (no `bedrock_version` header field). Each has a failing proof test that encodes the specification's reading, so none is prose-only.
- **Unavailable external evidence** (release attachments, external submissions, third-party reports): no finding was filed on this basis.

No skipped, mocked, parked or unrun test was treated as conformance: every pass row in the trace cites a concrete implementation anchor, every finding row cites a proof test that ran and failed, and the pass rows attest only what the first pass read at the cited lines. No finding in this audit is prose-only.

### contradicts-spec (proven violation)

#### Finding 1 (F-1e48e4e2) — GenesisTx::from_tx accepts a genesis inscription with trailing bytes after the three Cryptarchia parameters — **confirmed**, medium severity, high confidence

Cryptarchia Initialization says the genesis inscription "must also decode to exactly the three parameters, encoded as Cryptarchia Parameters specifies and with no trailing bytes", and that a node which cannot decode them "must reject the Genesis block". `valid_cryptarchia_inscription` calls `CryptarchiaParameter::decode`, which returns the unread remainder, and keeps only the decoded value, never checking the remainder is empty. An inscription that is the valid three-parameter encoding followed by arbitrary extra bytes is therefore a valid GenesisTx through both the builder path and the Deserialize path the node takes when it loads its deployment config. Two genesis files that differ only in trailing inscription bytes decode to the same parameters but have different transaction hashes, body roots and genesis ids, and the malformed one is not reported at node set-up. The finding shows no fund loss; it is a validation gap.

- Locations: `core/src/mantle/transactions/genesis_tx.rs:151-155` (`CryptarchiaParameter::decode(...)?.1`, the `rest` of the tuple is dropped); `binary-codec/src/canonical/bounded_vec.rs:157` (the codec leaves trailing bytes untouched by design).
- Repro: `cargo nextest run --locked -p logos-blockchain-core --all-features --test finding_20261022T024153_d7dd8c_1` → observed: "spec: the inscription must decode to exactly the three parameters with no trailing bytes, but GenesisTx::from_tx accepted an inscription with one trailing byte: Ok(GenesisTx { ... inscription: Bounded([24, 108, ..., 0, 170]) ... })". The exact-encoding control in the same test passes.
- Second pass: confirmed — independently read `valid_cryptarchia_inscription` (selects `decode(...).1` and drops the remainder); ran the proof: the exact-encoding control passed and the appended-byte rejection assertion failed because construction returned Ok.
- Fix: destructure the decode result as `(rest, parameter)` and return `Error::InvalidCryptarchiaParameter` when `rest` is not empty (or use a decode-all helper as `SignedOps::decode_all` does). The proof test then passes.

### off-by-requirement (proven violation)

#### Finding 5 (F-97a08a8b) — ChainId is bounded to 1..=255 bytes, so a zero-length chain id that the spec's u8 prefix encodes is rejected — **confirmed**, low severity, medium confidence

Cryptarchia Parameters defines chain_id as a "UTF-8 string, encoded with a u8 length prefix (at most 255 bytes)" and its encoding recipe writes `len(chain_id_enc).to_bytes(1, "little")`, which encodes an empty string as a 0x00 prefix. The only bound the spec states is the upper one. ChainId wraps `BoundedString<1, 255>`, so `ChainId::try_from("")` fails and `CryptarchiaParameter::decode` rejects an inscription whose length prefix is 0 with `LengthOutOfBounds { min: 1 }`. The lower bound is one byte stricter than the specification. The spec may well intend it (an empty chain identifier is useless for keeping networks disjoint), hence medium confidence, but as written the code and the document disagree. No runtime harm is shown.

- Locations: `core/src/mantle/transactions/genesis_tx.rs:241-246` (`MAX_CHAIN_ID_SIZE = u8::MAX`, `BoundedVec<u8, 1, MAX_CHAIN_ID_SIZE>`, `BoundedString<1, MAX_CHAIN_ID_SIZE>`); `genesis_tx.rs:685-691` (in-crate test pins the rejection of a 0 prefix).
- Repro: `cargo nextest run --locked -p logos-blockchain-core --all-features --test finding_20261022T024153_d7dd8c_5` → observed: "spec bounds chain_id to at most 255 bytes and states no minimum; a zero-length chain id must decode, but got: Some(LengthOutOfBounds { type_name: \"...Bounded<alloc::vec::Vec<u8>, 1, 255>\", len: 0, min: 1, max: 255 })".
- Second pass: confirmed — ran the proof (empty chain id fails with LengthOutOfBounds min=1); read both bounded aliases. Noted that a revised nonempty requirement in the spec would change the conclusion.
- Fix: lower the bound to `BoundedString<0, 255>` (and `BoundedVec<u8, 0, 255>` for decoding), or amend the spec to say the chain id is between 1 and 255 bytes. The proof test passes under the first option.

### missing-requirement (proven violations; finding 7 is a missing capability)

#### Finding 2 (F-aac31e5c) — Genesis transfer outputs are added to the UTXO set without output-note validation, so a zero-value genesis note is accepted — **confirmed**, medium severity, high confidence

Mantle Ledger Initialization says the genesis Transfer "is validated and executed as any other Transfer Operation, minus the two exemptions covering its inputs and the transaction balance. Its outputs are validated as Output Notes Validation requires", and the exemptions list is closed ("Everything else is validated as it would be in any other block"). The implementation's output-note validation is `Outputs::validate` (`core/src/mantle/ledger.rs:165-173`), which rejects zero-value notes and runs from a standard transfer's preverify. On the genesis path it never runs: `GenesisTx::from_tx` checks only that the transfer has no inputs, `into_genesis_ops` promotes the transfer to Verified with `into_state_trusted`, and `cryptarchia::LedgerState::from_genesis_tx` re-checks the inputs and calls `from_utxos` with every output unvalidated. A genesis block whose distribution includes a zero-value note initialises the ledger, giving the chain a UTXO no other block could ever have created. No fund loss is shown.

- Locations: `ledger/src/cryptarchia/mod.rs:721-735` (from_genesis_tx: "This is its verification", only `inputs.is_empty()` is checked); `ledger/src/lib.rs:575-605` (orchestration, no output validation); `core/src/mantle/transactions/genesis_tx.rs:74-77` (inputs only); contrast `core/src/mantle/ops/transfer.rs:128-135` (standard preverify validates outputs).
- Repro: `cargo nextest run --locked -p logos-blockchain-ledger --all-features --test finding_20261022T024153_d7dd8c_2` → observed: "spec: genesis transfer outputs are validated as Output Notes Validation requires, but a genesis transfer with a zero-value output note initialised the ledger". The well-formed distribution control passes.
- Second pass: confirmed — ran the proof (positive-value control passed; initialisation with an added zero-value output returned Ok); independently traced both entry points and found inputs checked only, while ordinary Transfer preverify calls `outputs.validate()`.
- Fix: call `operation.outputs.validate()` in `cryptarchia::LedgerState::from_genesis_tx` before `from_utxos` (mapping `OutputsError` into the existing `LedgerError::Outputs`), or validate in `GenesisTx::from_tx` next to the UnexpectedInput check so generator and config loader both report it. The proof test passes once either is in place.

#### Finding 8 (F-c8cd0cf4) — The genesis pow state copies an independent config value into epoch_pow_reward instead of deriving it from the reward pool — **confirmed**, low severity, medium confidence

Mantle Ledger Initialization says pow_reward_pool is set to POW_REWARD_POOL_GENESIS (5/1000 of the maximum supply, drawn from the initial token distribution) and that "epoch_pow_reward is derived from it by the computation given in Reward Pool". The ledger derives nothing: `PowState::from_reward_config`, reached from `LedgerState::from_genesis_tx`, sets `reward_pool` from `config.reward_pool_genesis` and `epoch_reward` from a second, unrelated field `epoch_reward_genesis`. `RewardPoWConfig::validate` does not check the two against each other; the only consistency check is a unit test in the node binary against the default settings.yaml. Any custom deployment can start with an epoch reward the Reward Pool computation does not yield for its pool. What the finding does not establish: the 5/1000-of-supply and drawn-from-the-distribution parts cannot be checked at all, because no maximum-supply constant exists and nothing relates the pool seed to the genesis outputs; those parts are low confidence.

### undefined-behaviour (proven violation, spec silent on the mapping)

#### Finding 3 (F-3bccd90f) — The ceremony tool converts each entropy source with fr_from_bytes and panics when its little-endian value is at or above the BN254 scalar modulus, which most real block hashes are — **confirmed**, medium severity, medium confidence

The Epoch Nonce Ceremony defines the entropy sources as the Bitcoin block hash r1, the Ethereum block hash r2 and the DRAND beacon value r3 and the genesis nonce as eta = H(r1, r2, r3) with H a zkhash. The spec does not say how a 32-byte hash becomes a field element. `inscribe` maps each source with `lb_groth16::fr_from_bytes`, which reads the bytes little-endian and errors when the integer is at or above the BN254 scalar modulus, and the generator `expect`s that result, panicking. The modulus is about 0.19 times 2^256 with most-significant byte 0x30, so any source whose last byte exceeds 0x30 is rejected: roughly four in five uniformly random Ethereum block hashes and DRAND values, and, because explorers display hashes big-endian, the Bitcoin hashes too. The ceremony as specified cannot be run on most of its inputs; operators would have to pre-reduce or truncate in an unspecified way, so different operators could derive different nonces from the same r1, r2, r3. Nodes are unaffected; the finding is confined to the ceremony tool.

- Locations: `tools/blockchain-tools/src/genesis/inscription.rs:38-40` (`fr_from_bytes(&bytes).expect("Invalid entropy source for Fr conversion")`); `zk/groth16/src/lib.rs:62-71` (fr_from_bytes rejects n >= modulus; `fr_from_mod_bytes` at line 74 reduces instead).
- Repro: `cargo nextest run --locked -p logos-blockchain-tools --all-features --test finding_20261022T024153_d7dd8c_3` → observed: "panicked at tools/blockchain-tools/src/genesis/inscription.rs:39:40: Invalid entropy source for Fr conversion: FrFromBytesError { parsed_bytes: \"50607000162736768413865283251298348907857627207201349845683772230799839985664\", modulus: \"21888242871839275222246405745257275088548364400416034343698204186575808495617\" }" with the Bitcoin genesis block hash as the only source. This target links the tools binaries; build it with a single job in a memory-constrained container.
- Second pass: confirmed — read `inscribe` lines 33-40 and `fr_from_bytes` lines 62-71; ran the proof with `CARGO_BUILD_JOBS=1` after an initial linker OOM and saw the stated panic on the real Bitcoin hash. Noted the replacement mapping remains unspecified.
- Fix: absorb each source in a way that accepts any 32 bytes (split each into two 16-byte limbs that are always below the modulus, or use `fr_from_mod_bytes`), and have the spec state the mapping so every operator derives the same eta. The proof test passes once a full-range 32-byte hash is accepted.

#### Finding 4 (F-2b5a9c8c) — Initial total stake D excludes every genesis note owned by the configured faucet key — **confirmed**, low severity, high confidence

#### Finding 6 (F-690a3f26) — The genesis nonce is decoded as a canonical little-endian BN254 scalar, so the spec's own example inscription is rejected — **confirmed**, low severity, high confidence

Cryptarchia Parameters describes genesis_epoch_nonce as "32 bytes, hex encoded" and appends `bytes.fromhex(GENESIS_EPOCH_NONCE)` to the inscription; the worked example gives the full inscription hex. `CryptarchiaParameter` stores the nonce as an `Fr`, and the codec decodes an `Fr` with `fr_from_bytes`, which requires the little-endian integer to be below the scalar field modulus. The code is arguably right: the nonce feeds the leadership circuit as a field element, and a ceremony that follows the spec always yields a canonical element.
