### Missing-requirement (proven violation)

#### Finding 1 (F-7db75f5d) — CHANNEL_CONFIG validation never checks `configuration_threshold <= len(keys)`, so an unreachable threshold is accepted and permanently locks the channel out of reconfiguration — **confirmed**, medium severity, high confidence

The specification's CHANNEL_CONFIG validation asserts, before any signature check, `assert config.configuration_threshold <= len(config.keys)` with the comment "The configuration threshold must be reachable with the accredited keys, otherwise the channel would be locked out of any future reconfiguration". The code enforces the four sibling assertions (both thresholds non-zero, keys non-empty, keys below 2^16) but never compares the new threshold with the new key count: not in the stateless preverify, not in the stateful verify, and nowhere else in the workspace. A config with threshold 2 and one key passes preverify and verify and is executed by the ledger, which stores the unreachable threshold. Every later CHANNEL_CONFIG then needs exactly 2 signatures at strictly increasing indexes below 1, which no proof can satisfy, so the channel can never again change its keys, round-robin parameters or thresholds. The gap applies to channel creation by anyone (empty proof) and to reconfiguration by the current committee. It is a consensus validity rule: a spec-conformant validator rejects the transaction and this implementation accepts it. The finding does not show fund loss; inscriptions, deposits, withdrawals and transfers keep working under the frozen configuration.

- Locations: `core/src/mantle/ops/channel/config.rs:109-121` (preverify: checks zero thresholds and empty keys only), `core/src/mantle/ops/channel/config.rs:130-198` (verify: authorizes against the old state, never compares new threshold to new keys), `core/src/mantle/ops/channel/config.rs:217-226` (execute stores the threshold), `core/src/mantle/ops/signed_op.rs:130-133` (into_preverified dispatch), `ledger/src/mantle/mod.rs:204-221` (`try_apply_channel_config`).

### Spec-drift (documentation drift inside the specification, prose-only)

#### Finding 2 (F-58202e02) — The specification's `round_robin` pseudo-code divides by `posting_timeframe` without a zero guard, undefined on every default channel; the code follows the `0 = infinity` annotation instead — **disputed**, info severity, low confidence
