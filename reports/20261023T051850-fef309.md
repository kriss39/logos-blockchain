### wrong-default (proven violation)

#### Finding 2 (F-6d9e8c5d) — During the genesis epoch `last_voucher_root` is the field element 0 from `RewardsRoot::default()`, not the root of the empty voucher tree — **confirmed**, info severity, high confidence

The specification's Validate block requires `assert claim.rewards_root == last_voucher_root`, where `last_voucher_root` is "the last root of the voucher Merkle tree at the start of the epoch". At the start of epoch 0 the voucher tree is empty, and the ledger's own voucher MMR reports its root as `frontier_root()` = `empty_subtree_root(33)` = 6898860929736031474121651521161139261035492205636414278575472746649883062581. The code instead initialises the snapshot with `RewardsRoot::default()`, which is Fr 0, and only replaces it on the first header of a later epoch. Throughout the genesis epoch every LEADER_CLAIM root check compares against 0. The finding does not establish any change in claim outcome: no voucher exists in epoch 0, so no claim can succeed under either root. The observable effect is the value the ledger reports to the chain-leader and wallet services and the error class a client gets (VouchersRootMismatch rather than an invalid proof) when it follows the worked example in epoch 0.

- Locations: `ledger/src/mantle/leader.rs:72` (`root: RewardsRoot::default()` inside `LeaderState::new()`; the empty MMR is built separately at line 78), `ledger/src/mantle/leader.rs:109-123` (`update_epoch_state` snapshots only when the incoming epoch is greater), `core/src/mantle/ops/leader_claim.rs:45-46` (`#[derive(Default)]` on `RewardsRoot`), `ledger/src/mantle/mod.rs:136-138` (`vouchers_snapshot_root()` read by validation).
- Repro: `cargo nextest run --locked -p logos-blockchain-ledger --all-features --test spec_20261023T051850_fef309_2 last_voucher_root_at_the_start_of_the_genesis_epoch_is_the_empty_voucher_tree_root` → observed: `assertion `left == right` failed: last_voucher_root at the start of the genesis epoch must be the root of the (empty) voucher Merkle tree / left: 0 / right: 6898860929736031474121651521161139261035492205636414278575472746649883062581` at `ledger/tests/spec_20261023T051850_fef309_2/main.rs:128`; exit 100.
- Second pass: confirmed — ran the exact repro command on the proof checkout (exit 100, same assertion and values), then independently read `LeaderState::new` and `update_epoch_state` and concluded every epoch-zero root check uses zero instead of the tree root at epoch start, "without claiming a valid genesis-epoch claim can exist". It also verified the refs: proof HEAD `1b5a45a8c4a2c7a37b807f427cadfcc81962cf23`, parent and local `0.3.0` tag → `f76be2dde171711299eb9c25ec7cc6a3821fe240`, and `git diff` against the tag object `1da2d9d6…` for all five unit files is empty.
- Merge-pass adjudication: not applicable (first-pass finding; status set by the second pass's verdict). The merge pass re-read `ledger/src/mantle/leader.rs:66-80, 109-154` and confirms the description of the code.
- Fix: in `LeaderState::new()` set `root: MerkleMountainRange::<VoucherCm, ZkHasher>::new().frontier_root().into()`, or build the snapshot through `snapshot_vouchers()` on the fresh state. Optionally remove `Default` from `RewardsRoot` so 0 can no longer stand in for a tree root. The proof test fails today and passes after the change.

### undefined-behaviour (section silent; contradicts the Ledger section's output rule)

#### Finding 1 (F-311ed683) — LEADER_CLAIM with a rounded-down share of 0 is accepted: the voucher nullifier is consumed and a zero-value note is inserted into the ledger — **disputed**, medium severity, medium confidence

The LEADER_CLAIM Execution block says: step 1 "Add `claim.voucher_nf` to the `voucher_nullifier_set`"; step 2 "construct a single output note with value `leader_reward` under the public key defined in the payload, and insert it into the Ledger"; step 3 reduce `leaders_rewards` by the same amount. It says nothing about `leader_reward = 0`. When the per-voucher share ⌊leaders_rewards / unclaimed vouchers⌋ is 0 (an empty pool, or a pool smaller than the number of unclaimed vouchers), the code does exactly those three steps with amount 0: `execute` at `core/src/mantle/ops/leader_claim.rs:283-311` builds `Note { value: 0, pk: claim.public_key }` from `context.reward_amount` and inserts it, `verify` at lines 248-274 places no condition on the share, and the ledger feeds in `LeaderState::reward_amount()` (`ledger/src/mantle/leader.rs:175-183`) which is 0. The first pass holds this to be a defect because the same specification's Ledger section (Output Notes Validation) requires `note.value > 0` for every note inserted into the Ledger, a rule the code enforces for TRANSFER and CHANNEL_TRANSFER outputs via `OutputsError::ZeroValueNote` (`core/src/mantle/ledger.rs:165-173`) but not here, and because the sibling CLAIM_POW_REWARD guards its payout with `assert epoch_pow_reward > 0`. The consequences the first pass names: a zero-value UTXO in consensus state that an implementation applying the output rule would never create, and a voucher burnt for nothing, forfeiting its share of later rewards since the pool is kept for unclaimed vouchers across epochs. The finding does not establish fund loss beyond that forfeited future share, and it does not establish a divergence from the literal text of the LEADER_CLAIM section itself.

- Locations: `core/src/mantle/ops/leader_claim.rs:293-297` (note built from `context.reward_amount` and inserted; pool reduced with unchecked `-=`), `core/src/mantle/ops/leader_claim.rs:248-274` (`verify`: nullifier and root checks only, no share condition), `ledger/src/mantle/leader.rs:175-183` (`reward_amount()` = `checked_div(...).unwrap_or(0)`).
- Repro: `cargo nextest run --locked -p logos-blockchain-ledger --all-features --test spec_20261023T051850_fef309_1 leader_claim_with_a_zero_share_does_not_insert_a_zero_value_note` → observed: `Output Notes Validation requires `note.value > 0` for every note inserted into the Ledger, yet executing LEADER_CLAIM inserted [Utxo { op_id: [226, 186, 213, 151, ...], output_index: 0, note: Note { value: 0, pk: PublicKey(2010594) } }] (...; voucher_nf now in the nullifier set: true)` at `ledger/tests/spec_20261023T051850_fef309_1/main.rs:364`; exit 100. The test drives the real block path (`Ledger::prepare_update` / `verify_batch_proofs` / `commit_update`) with a genesis stake equal to STAKE_TARGET so that epoch 0 accrues no leader reward, then applies the section's worked example transaction in the first block of epoch 1. The control test in the same file, `example_claim_with_a_positive_share_mints_one_note_of_the_share`, uses a 10_000_000 stake and passes, minting one note of value 38, which shows the construction is a valid claim.
- Second pass: rejected — ran the exact repro command on the proof checkout (exit 100, assertion at `main.rs:364`, zero-value note and consumed nullifier reproduced) and the positive-share control (passed). Its reasoning, verbatim: "This reproduces the behavior, but not a divergence from the supplied authoritative section. Execution step 2 says 'construct a single output note with value leader_reward under the public key defined in the payload, and insert it into the Ledger'; step 1 says 'Add claim.voucher_nf to the voucher_nullifier_set.' Neither the validation assertions nor execution qualifies this with leader_reward > 0. core/src/mantle/ops/leader_claim.rs:293 has `let utxo = operation.utxo(context.reward_amount);`, :294 inserts it, :290 inserts the nullifier, and :297 subtracts the same amount, matching those instructions even when the amount is zero. The failing test adds a positivity requirement from an Output Notes Validation section not supplied here; the sibling CLAIM_POW_REWARD rule does not establish a LEADER_CLAIM requirement. A global rule expressly applying to these minted notes could change this assessment, but the supplied section does not support the claimed defect."
- Merge-pass adjudication: not applicable (first-pass finding; status set by the second pass's verdict). The merge pass re-read `core/src/mantle/ops/leader_claim.rs:242-312`, `ledger/src/mantle/leader.rs:173-183` and `core/src/mantle/ledger.rs:165-173` and confirms both passes' description of the code; it did not re-run the test.
- Disposition: both passes agree on the facts: the zero-share claim is accepted deterministically, the nullifier is consumed, a `Note { value: 0 }` is inserted, the pool is reduced by 0, and the three Execution steps are followed literally. In dispute is the clause interpretation: whether a LEADER_CLAIM conformance finding may draw on the Ledger section's Output Notes Validation (`note.value > 0` for every note inserted into the Ledger) and the CLAIM_POW_REWARD guard as context for what the silent section requires, as the first pass does, or whether only the staged LEADER_CLAIM section's own text binds, as the second pass holds. The second pass states that a global rule expressly applying to minted notes would change its assessment; the first pass's position is that the Output Notes Validation is such a rule. The report records the finding as disputed and leaves the clause question to the specification's owners.
- Fix: settle the zero-share rule in both documents. The option closest to the rest of the specification mirrors CLAIM_POW_REWARD: add `assert leader_reward > 0` to the LEADER_CLAIM Validate block, expose the share to verification (e.g. `OperationVerificationHelper::get_leader_reward_amount()` backed by `LeaderState::reward_amount()`), carry it in `LeaderClaimVerificationContext`, and return a new `LeaderClaimError` variant from `verify` when it is 0 so the voucher stays claimable once the pool is refilled. Use `checked_sub` for the pool reduction while there. If the specification is instead amended to permit a zero-value claim note, the Ledger section must carve out LEADER_CLAIM explicitly. The proof test fails today and passes under either code fix; the control test must keep passing.
