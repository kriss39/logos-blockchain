### Spec-drift (proven violation — failing test; drift judged to lie in the document)

#### Finding 1 (F-687bba39) — Mantle transaction has no Ledger Transaction component; the spec's two-part transaction shape no longer exists — **confirmed**, low severity, high confidence

The overview (§Bedrock Mantle) states: *"Mantle Transactions consist of a sequence of Operations together with a Ledger Transaction used for paying fees and transferring funds."* The implemented Mantle transaction — `SignedOps`, re-exported at `core/src/mantle/mod.rs:15` and defined as `TxList<SignedOp>` in `core/src/mantle/transactions/tx_list/signed_ops.rs:38` — is exactly a bounded list of operations paired with proofs, with no Ledger Transaction component; no `LedgerTx` type exists anywhere in the workspace. Fund movement is performed by the optional `Transfer` *operation* variant inside the same operation sequence (applied at `ledger/src/lib.rs:876-886`), and fees are paid out of whatever balance the transaction's Transfer operations leave over (`ledger/src/lib.rs:510`). A transaction consisting of a single channel inscription is complete and well-formed. The code is internally consistent — the ledger-transaction role was folded into the operation set — so the drift is in the document, which still describes the older two-part shape. The finding does not establish any fund loss, fee bypass, or acceptance of an invalid transaction; it is a representation divergence between the published overview and the implementation.

- Locations: `core/src/mantle/mod.rs:15` (the `SignedOps` transaction type), `ledger/src/lib.rs:876-886` (Transfer applied as an ordinary operation in the per-op loop).
- Repro: `cargo test --locked -p logos-blockchain-core --all-features --test finding_20261015T061023_0d49c9_1` → observed: the test builds a well-formed Mantle transaction containing a single ChannelInscribe operation and fails on the assertion *"spec drift: OVERVIEW-BEDROCK-ARCHITECTURE says a Mantle Transaction consists of Operations together with a Ledger Transaction, but `SignedOps` is only a sequence of (operation, proof) pairs — this valid transaction carries no ledger-transaction (funds/fee) component at all"* (`test result: FAILED. 0 passed; 1 failed`).
- Second pass: confirmed — re-ran the test (compiled, exited 101 at the assertion on line 57) and independently read `core/src/mantle/mod.rs:15`, `signed_ops.rs:38` and `from_parts`, the `TxList` representation, and `ledger/src/lib.rs:484-520, 876-886, 928-979`: `SignedOps` consists exclusively of signed operations; a Transfer participates in the ordinary operations loop and contributes to its running balance, from which fees are computed; there is no separate ledger-transaction component. It noted the test uses an unverified placeholder signature, so it proves construction/representation rather than end-to-end ledger acceptance of a fee-charged inscription-only transaction, and that it did not independently establish the finding's historical claim that a newer design folded the ledger transaction into the operations.
- Fix: update the overview's §Bedrock Mantle to describe the implemented shape — a Mantle Transaction is a bounded sequence of Operations, each with its proof, where funds transfer and fee funding are performed by optional Transfer operations within the sequence. If a mandatory Ledger Transaction is instead the intended design, add that component to `SignedOps`/`Ops` and require it at verification, at which point the proof test (`core/tests/finding_20261015T061023_0d49c9_1.rs`) passes as written.

### Spec-drift (unavailable external evidence — no mainnet configuration in the tree)

#### Finding 2 (F-a87c93f9) — Spec's 2160-block finality depth appears nowhere; every shipped configuration sets security_param 120 or 30 — **unconfirmed**, info severity, low confidence

The overview's sequence diagram states *"Block finalizes after being buried by 2160 blocks."* In the code, the burial depth at which a block is treated as final (and states pruned) is the Cryptarchia `security_param` (`consensus/cryptarchia-engine/src/config.rs`, outside the audited unit, read for tracing). There is no compiled-in default of 2160 and the literal appears nowhere in the workspace's code or configuration; the node's embedded deployment settings and the 0.3.0 genesis-ceremony templates set `security_param` to 120 (testnet/devnet) or 30 (standalone). A reader of the overview expects 2160-block finality; a node built from this tree finalizes at 120 or 30. This is a prose-and-configuration finding only — no code in the unit implements finality, so no unit test can demonstrate it — and it is plausibly intentional testnet parameterization of a mainnet-targeted spec number. It does not establish that any intended production deployment violates the figure: no mainnet configuration exists in the tree to compare.

- Locations: none in the unit (the divergence cannot be anchored to a unit file); the configuration values live at `nodes/node/binary/src/config/deployment/settings.yaml:25` and `deployment/ceremony/genesis/{testnet,devnet,standalone}/deployment-template.yaml:23`, and the depth is consumed at `consensus/cryptarchia-engine/src/lib.rs:49-70`.
- Repro: `sh test/2/show_configured_finality_depth.sh` → observed: `security_param: 120` for the embedded settings and the testnet/devnet templates, `security_param: 30` for standalone, then "no occurrence of 2160" from a whole-word grep across consensus, core, ledger, nodes, deployment and services (exit 0).
- Second pass: unclear — re-ran the script (exit 0, same values, no 2160) and independently read `consensus/cryptarchia-engine/src/lib.rs:62-73` (in Online state, the last immutable block is the local-chain ancestor at `security_param` depth), so the reported deployment behaviour is real. But the spec sentence is a sequence-diagram annotation that does not say which deployment the number governs or whether test networks must retain it; no mainnet configuration is provided to establish that the intended production setting violates it, the implementation point is outside the unit, and a configurable depth with no compiled default does not by itself contradict the annotation. Clarifying whether the overview mandates 2160 for every deployment, or names a production parameter while permitting test-network overrides, would settle the question.
- Fix: either state in the overview that the finality depth is the deployment's Cryptarchia `security_param` (giving 2160 as the mainnet value), or add the 2160 value to the mainnet deployment parameters when they exist. A conformance check would assert that the mainnet deployment template's `security_param` equals the spec's published finality depth.
