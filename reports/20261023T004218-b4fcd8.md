### contradicts-spec (proven violations)

#### Finding 1 (F-2b761887) — the priority tip is `(balance as u64) − fee`, not `checked_uint64(tx_balance − fee)`; a tip above UINT64_MAX is accepted wrapped and a valid tip is rejected — **confirmed**, medium severity, high confidence

The specification (Mantle Transaction > Validation, step 3) reads: `assert tx_mandatory_fee <= tx_balance; tx_priority_tip = checked_uint64(tx_balance - tx_mandatory_fee)`, where `tx_balance` is the signed 128-bit accumulator of step 2, and the Arithmetic section adds that "a Mantle Transaction is invalid if any intermediate or final result cannot be represented in that type; results must never silently wrap around or saturate". `LedgerState::try_apply_transaction` performs the `<=` check correctly on the i128 balance, then computes the tip as `GasCost::from(balance as Value).checked_sub(fee_burned)?`. The `as` cast keeps the low 64 bits of the balance, so the tip is `(tx_balance mod 2^64) − fee`. When `tx_balance − fee > UINT64_MAX` the spec invalidates the transaction and its block, but the ledger accepts it whenever the truncated balance covers the fee, credits the wrapped tip to the leader through `GasAndFees.fee_tip`, and leaves 2^64 units of consumed value neither burned, tipped nor recreated. When `tx_balance − fee ≤ UINT64_MAX` but the truncated balance is below the fee, a valid transaction is rejected with `GasOverflow`. The finding establishes a consensus-validity divergence and an accounting gap; it does not show fund theft. The location is outside the unit's listed paths but is the only implementation of this step, and the result lands in the unit's `GasAndFees`. Reachability on the shipped deployment: the embedded genesis gives the faucet key a note of exactly UINT64_MAX.

- Locations: `ledger/src/lib.rs:514-515` (tip computed from `balance as Value`), `ledger/src/gas_and_fees.rs:13` (`fee_tip` field that carries the wrapped value into block accounting), `ledger/src/lib.rs:510` (the correct i128 fee check just above).
- Repro: `cargo test --locked -p logos-blockchain-ledger --all-features --test 20261023T004218-b4fcd8-1` → observed: exit 101, 0 passed, 2 failed. `a_tip_above_uint64_max_makes_the_transaction_invalid` (balance 18446744073710551615, fee 1507, spec tip 18446744073710550108 > UINT64_MAX): "try_apply_transaction -> Ok(GasAndFees { execution_gas: Gas(1180), storage_gas: Gas(327), fee_burned: GasCost(1507), fee_tip: GasCost(998492) }); whole block -> Ok(Ok(()))". `a_tip_within_uint64_is_valid_even_when_the_balance_is_not` (balance 18446744073709551621, spec tip 18446744073709550114 fits): "Err(GasOverflow(GasOverflow))".
- Second pass: confirmed — ran the same command independently and saw both tests fail with the same outputs; read `ledger/src/lib.rs:492-515` and confirmed the fee comparison widens the fee to Balance while the tip narrows the balance with `balance as Value` before subtraction, discarding the high bits, which contradicts Validation step 3.
- Merge-pass adjudication: not applicable (raised by the first pass). The merge pass re-read `ledger/src/lib.rs:510-515` on the proof branch and confirmed the cited lines are as both passes describe.
- Disposition: not applicable (confirmed).
- Fix: compute the tip on the i128 balance with a checked conversion, e.g. `let fee_tip = GasCost::from(Value::try_from(balance - Balance::from(total_gas_cost.into_inner())).map_err(|_| LedgerError::BalanceOverflow)?);` and avoid `as` casts on `Balance`. The first pass verified both proof cases pass with this change and reverted it. Keep `ledger/tests/20261023T004218-b4fcd8-1/main.rs` as the regression test.

#### Finding 2 (F-d7ca2378) — a TRANSFER's inputs and outputs are summed in u64 before widening, so a transfer whose inputs or outputs add up past UINT64_MAX is rejected though the spec's int128 balance never overflows — **confirmed**, low severity, high confidence

The specification (Mantle Transaction > Validation, step 2) reads: `tx_balance = 0   # Signed 128-bit accumulator`, then for every TRANSFER `for inp in op.inputs: tx_balance = checked_int128(tx_balance + get_value_from_note_id(inp))` and `for out in op.outputs: tx_balance = checked_int128(tx_balance - out.value)`; the Arithmetic section adds "The transaction balance uses a signed 128-bit integer". The only overflow bound on summed note values is therefore int128. The ledger instead takes each TRANSFER's contribution from `TransferOp::balance`, which first computes `self.inputs.amount(utxos)?` and `self.outputs.amount()?` as u64 sums (failing with `InputsOverflow` / `OutputsOverflow`) and only then widens to i128. A TRANSFER whose inputs or outputs total more than UINT64_MAX therefore fails the whole transaction and its block, which the section does not allow. Spec-valid transactions are rejected; there is no state corruption. The location is outside the unit's listed paths; this step has no implementation inside the unit. Both passes note that if the Operations section's own TRANSFER definition bounds a single transfer's sums to uint64, the two sections disagree and the document needs reconciling; the finding is adjudicated against the Mantle Transaction section the brief staged as authoritative. Reachability: the embedded genesis gives the faucet key a note of exactly UINT64_MAX, so spending it with any other note in one TRANSFER triggers the rejection.

- Locations: `core/src/mantle/ops/transfer.rs:58-69` (`TransferOp::balance`, widens u64 subtotals), `core/src/mantle/ledger.rs:377-388` (`Inputs::amount`, `InputsOverflow`), `core/src/mantle/ledger.rs:182-190` (`Outputs::amount`, `OutputsOverflow`); called from `ledger/src/cryptarchia/mod.rs:579` via `ledger/src/lib.rs:876-886`.
- Repro: `cargo test --locked -p logos-blockchain-ledger --all-features --test 20261023T004218-b4fcd8-2` → observed: exit 101, 0 passed, 2 failed. `a_transfer_whose_inputs_add_up_past_uint64_is_valid` (inputs [UINT64_MAX, UINT64_MAX], outputs [UINT64_MAX], spec balance 18446744073709551615): "Err(Mantle(Transfer(Inputs(InputsOverflow))))". `a_transfer_whose_outputs_add_up_past_uint64_is_valid` (outputs [UINT64_MAX, 1000000], spec balance 100000): "Err(Mantle(Transfer(Outputs(OutputsOverflow))))".
- Second pass: confirmed — ran the same command independently and saw both tests fail with `InputsOverflow` and `OutputsOverflow`; read `TransferOp::balance` and `Inputs::amount` / `Outputs::amount` and confirmed both sums are checked u64 computations widened to i128 only afterward, while step 2 accumulates directly in the signed 128-bit accumulator. It noted the conclusion is against the supplied authoritative section and that a narrower Operations-section bound would require reconciling the sections.
- Merge-pass adjudication: not applicable (raised by the first pass). The merge pass re-read `core/src/mantle/ops/transfer.rs:58-69` on the proof branch and confirmed the u64 subtotals are computed before the i128 widening.
- Disposition: not applicable (confirmed).
- Fix: in `TransferOp::balance`, iterate the inputs, look each up in `utxos` (`InexistingNote` on a miss) and `checked_add` its value into the i128; then `checked_sub` each output's value; stop using `Inputs::amount` / `Outputs::amount` for the balance. If the Operations section is meant to bound a single TRANSFER's sums to uint64, correct the Mantle Transaction section instead so the two agree. The first pass verified both proof cases pass with the code change and reverted it. Regression test: `ledger/tests/20261023T004218-b4fcd8-2/main.rs`.

#### Finding 3 (F-ba7ae485) — `impl Add for GasPrice` adds two fee prices with a bare `+` that wraps silently in release builds and panics in debug; no caller exists today — **disputed**, info severity, medium confidence

The specification (Mantle Transaction > Arithmetic) reads: "All arithmetic in this specification is checked. Every addition, subtraction, and multiplication over token values, balances, gas amounts, and fees is performed on the stated integer type, and a Mantle Transaction is invalid if any intermediate or final result cannot be represented in that type; results must never silently wrap around or saturate". `Gas` and `GasCost` expose only checked operations, but `GasPrice` gets `impl std::ops::Add` as `Self(self.0 + rhs.0)` with `Output = Self`, which cannot report an overflow: without overflow checks (the workspace's release profile) `GasPrice::new(u64::MAX) + GasPrice::new(1)` returns `GasPrice(0)`; with them it panics. No code in the workspace calls the operator. The finding establishes an unchecked operator on a fee type and nothing about reachable transaction behaviour; the first pass filed it as a latent divergence at info severity, and the second pass rejected it as a violation of the section.

- Locations: `core/src/mantle/gas.rs:57-63` (`impl Add for GasPrice`, bare `+` at line 61).
- Repro: `cargo test --locked -p logos-blockchain-core --all-features --config 'profile.test.package."logos-blockchain-core".overflow-checks=false' --test 20261023T004218-b4fcd8-3 -- gas_price_addition_never_wraps_or_aborts` → observed: exit 101, 1 failed: "Spec Arithmetic: results must never silently wrap around. GasPrice::new(u64::MAX) + GasPrice::new(1) silently wrapped to GasPrice(0)." Under the default test profile the same test fails with "panicked at core/src/mantle/gas.rs:61:14: attempt to add with overflow".
- Second pass: rejected — "Ran its exact repro command with overflow-checks=false: it failed because GasPrice(MAX) + GasPrice(1) returned GasPrice(0). The unchecked operator is real, but the test does not demonstrate a divergence of a specified transaction computation. The qualifying spec sentence is "All arithmetic in this specification is checked" and the consequence is "a Mantle Transaction is invalid if any intermediate or final result cannot be represented in that type". The specified mandatory fee computation multiplies gas by a price and adds fee amounts; it never adds two prices. Independently read the actual path: ledger/src/lib.rs:498-501 invokes GasCost::calculate twice and execution_base_fees.checked_add(permanent_storage_fees); core/src/mantle/gas.rs:80-85 implements calculate with checked_mul and lines 93-94 implement checked_add with u64::checked_add. Searched GasPrice uses and found no production caller of its Add implementation. The line `Self(self.0 + rhs.0)` at gas.rs:61 is a latent API hazard, not a presently violated transaction requirement. A production/spec-defined calculation invoking it would change this verdict."
- Merge-pass adjudication: not applicable (raised by the first pass). The merge pass re-read `core/src/mantle/gas.rs:57-63` on the proof branch and confirmed the operator is as described.
- Disposition: both passes agree on the facts: the operator is unchecked, it wraps to `GasPrice(0)` with overflow checks off and panics with them on, the specified fee path (`GasCost::calculate` twice, then `checked_add`) is fully checked, and nothing calls `GasPrice`'s `Add`.
