### contradicts-spec (failing unit test on the helpers; disputed as a spec divergence)

#### Finding 1 (F-975953d5) — The two helpers documented as `assert_spendable` accept an empty input list; `len(inputs) > 0` is checked only in the separate `Inputs::preverify` — **disputed**, low severity, high confidence

The specification's `assert_spendable(inputs, channel_id)` begins with `assert len(inputs) > 0`, then checks uniqueness, presence, service-note status and channel ownership. In `core/src/mantle/ledger.rs`, `validate_not_in_channel` is documented as "the `assert_spendable(inputs, None)` case of the spec" and `validate_in_channel` as "the `assert_spendable(inputs, channel_id)` case of the spec". Both run the uniqueness, service-note, presence and channel checks but never check emptiness, so for an empty `Inputs` every check holds vacuously and both return `Ok(())`. Non-emptiness is enforced only by the stateless `Inputs::preverify`. Every caller at 0.3.0 (Transfer, ChannelDeposit, ChannelTransfer, ChannelWithdraw) runs `preverify` before its verify step reaches the helpers, so no ledger path accepts an operation with empty inputs today. The finding does not establish any reachable acceptance of an empty-input operation, any fund loss, or any consensus divergence; it pins the gap between the helpers' documented contract and the spec function they name.

- Locations: `core/src/mantle/ledger.rs:302-317` (`validate_not_in_channel`, no emptiness check), `core/src/mantle/ledger.rs:324-339` (`validate_in_channel`, no emptiness check), `core/src/mantle/ledger.rs:291-296` (`Inputs::preverify`, the only `EmptyInputs` return), callers `core/src/mantle/ops/transfer.rs:132,152`, `ops/channel/deposit.rs:105,133`, `ops/channel/channel_transfer.rs:108,150`, `ops/channel/withdraw.rs:87,126`.
- Repro: `cargo test --locked -p logos-blockchain-core --all-features --test 1` (artifact `core/tests/1/main.rs`, expect nonzero) → observed: "assertion `left == right` failed: spec: assert_spendable(inputs, None) must assert len(inputs) > 0 / left: Ok(()) / right: Err(EmptyInputs)" and the same for the `channel_id` case; "test result: FAILED. 0 passed; 2 failed".
- Second pass: rejected — ran the same command and reproduced both assertion failures, then wrote: "This reproduces the helper behavior, but not a spec divergence. The spec requires 'assert len(inputs) > 0'; core/src/mantle/ledger.rs:291-296 implements exactly that as `if self.is_empty() { return Err(InputsError::EmptyInputs); }`. Transfer preverify calls `operation.inputs.preverify()?` (core/src/mantle/ops/transfer.rs:132); Deposit, ChannelTransfer and ChannelWithdraw do likewise before their Preverified verification invokes the stateful helpers. LedgerState::try_apply_transaction requires PreverifiedMantleTransaction. Ran the core --lib preverify_rejects_ filter: 17 passed, including all four empty-input rejection tests. The specification does not require the stateless and stateful checks to reside in one Rust method; the comments do not override the working validation pipeline."
- Disposition: both passes agree on the facts: the two helpers return `Ok(())` for empty inputs, `Inputs::preverify` rejects them, every caller at 0.3.0 preverifies first, and the ledger entry point requires a preverified transaction. The dispute is whether a spec function split across two Rust methods, with the first assertion only in the stateless half, counts as the code contradicting `assert_spendable` (first pass) or as a conforming pipeline with a misleading doc-comment (second pass).
- Fix: start both `validate_not_in_channel` and `validate_in_channel` with `self.preverify()?;` (or an inline `if self.is_empty() { return Err(InputsError::EmptyInputs); }`), keeping `Inputs::preverify` as the cheap early rejection; `core/tests/1/main.rs` fails today and passes once the check is in place. If the project prefers the current split, correct the two doc-comments so they no longer claim to be the whole of `assert_spendable`.

### undefined-behaviour (failing unit test on the tree; disputed as a spec divergence)

#### Finding 2 (F-ac85a371) — Inserting a NoteId already in `UtxoTree` appends a second leaf and overwrites the dictionary entry, so the spent note stays committed in the root and a serde round trip changes the root — **disputed**, low severity, medium confidence

The specification keeps notes in "a dictionary mapping the NoteId to the note", and `execute_spending`'s `ledger.remove` "updates the merkle tree to zero out the leaf for this entry". It says note ids are unique but not what `ledger.add` does with an id already present. In the code, `ledger.add` is `Outputs::execute`, which calls `UtxoTree::insert`, which calls `MerkleTree::insert`. That allocates a new leaf at the lowest free index, then overwrites `items[key]` with the new position, without checking whether the key exists. The earlier leaf stays in the tree, unreachable from the dictionary, so nothing can ever zero it. After the note is spent, the note root still commits to the spent NoteId, and PoL proves membership against that root. The tree also reports 2 leaves for 1 note. Serialization stores only the dictionary, so a node that reloads its ledger state computes a different note root from one that did not. Every note-creating path traced at 0.3.0 derives a fresh NoteId, so the behaviour is latent; the finding does not establish a reachable duplicate insert, a fund loss or a live consensus split.

- Locations: `merkle/utxotree/src/lib.rs:154-157` (`UtxoTree::insert`, no presence check), `core/src/mantle/ledger.rs:175-180` (`Outputs::execute`, the spec's `execute_adding`), `merkle/tree/src/lib.rs:174-185` (`MerkleTree::insert` allocates then overwrites), `merkle/tree/src/lib.rs:207-222` (`remove` zeroes only the mapped position), `merkle/tree/src/lib.rs:229-237` (`compressed` built from `items` only), `merkle/utxotree/src/lib.rs:227-254` (serde via `compressed`).
- Repro: `cargo test --locked -p logos-blockchain-utxotree --all-features --test 2` (artifact `merkle/utxotree/tests/2/main.rs`, expect nonzero) → observed: three failures: "spec: removing the note zeroes its leaf, so the root of a ledger holding no notes must be the empty root" (roots differ), "spec: the Merkle tree commits to the notes of the NoteId -> note dictionary, one leaf per note / left: 2 / right: 1", "a node that reloads its ledger must compute the same note root" (roots differ); "test result: FAILED. 0 passed; 3 failed".
- Second pass: rejected — ran the same command and reproduced all three failures, independently read `UtxoTree::insert/remove` and `MerkleTree::insert/remove/compressed`, and wrote: "This is a real generic-container robustness issue, but the provided spec says 'These note identifiers uniquely define notes in the system and cannot be chosen by the user' and defines creation by deriving the ID from each operation and output index. It specifies no replacement, idempotency, or rejection rule for inserting an already-existing ID. The proof inserts one ID twice directly, without a ledger operation sequence that can do so. Consequently it does not demonstrate nonconformance on the specified unique-note execution domain. … A reachable repeated-ID execution or an explicit duplicate-add contract would change this assessment." It also ran the utxotree lib suite: 14 passed.
- Disposition: both passes agree that a repeated insert leaves an orphan leaf, that `remove` and serde ignore it, and that no path at 0.3.0 was found that re-derives an existing NoteId (Transfer/Deposit/ChannelTransfer consume inputs; LeaderClaim and ClaimPowReward nullifiers block replay; SDP reward op ids are per finalized epoch; genesis indices are distinct). The dispute is whether "a dictionary mapping the NoteId to the note" plus "zero out the leaf for this entry" implies a dictionary-semantics requirement on `add` that the tree violates (first pass), or whether the section leaves duplicate-add unspecified so the behaviour cannot contradict it (second pass).
- Fix: give `UtxoTree::insert` (or `MerkleTree::insert`) dictionary semantics for a present key: either replace the leaf in place at the existing position, as `MerkleTree::update` does, or refuse the insert and have `Outputs::execute` surface a new `OutputsError` variant. With the in-place option `merkle/utxotree/tests/2/main.rs` passes; with the refusing option, replace it with a test asserting the second insert is rejected and `size()` equals `utxos().size()`.

#### Finding 3 (F-ba65d4aa) — The spec recycles freed leaf indices into "the list of unused leaves" but never says which one `ledger.add` takes; `UtxoTree` always takes the lowest free index, and the choice changes the consensus-relevant note root — **disputed**, low severity, low confidence (prose-only: the proof passes by design)

`execute_spending` says `ledger.remove` "updates the merkle tree to zero out the leaf for this entry and adds that leaf index to the list of unused leaves", and `execute_adding` calls `ledger.add(output_note_id)`. The section never says in what order unused leaves are reused, or whether they come before never-used leaves. The code keeps no list: `UtxoTree::insert` reaches `DynamicMerkleTree::insert`, which always fills the smallest free index whatever order indices were freed in. Leaf positions determine the note root, which is consensus state (PoL proves membership against the aged note root), and the repository generates conformance vectors for an alternative implementation. Two implementations that both follow this text but pick different unused leaves would compute different roots. The code's choice is reasonable and documented in dynamic-merkle; the gap is that the spec does not pin it. The finding does not establish any divergence within this Rust implementation, which applies one policy consistently, and it names no sentence the code contradicts.

- Locations: `merkle/utxotree/src/lib.rs:159-162` (`UtxoTree::remove`), `merkle/utxotree/src/lib.rs:154-157` (`UtxoTree::insert`), `merkle/dynamic-merkle/src/lib.rs:424-455` (`first_empty_index()`, documented at `:5-7`, `:427-429`), `core/src/mantle/ops/mod.rs:34-40` (conformance vectors for the nim implementation).
- Repro: `cargo test --locked -p logos-blockchain-utxotree --all-features --test 3 -- --nocapture` (artifact `merkle/utxotree/tests/3/main.rs`, kind command, expect zero) → observed: "leaves freed in order: [3, 1, 4] / leaves reused (UtxoTree): [1, 3, 4] / note root, lowest-free policy: 2092…2674 / note root, LIFO list policy: 1451…6413 / test result: ok. 1 passed".
- Second pass: rejected — ran the same command, saw the same indices and differing roots, read `DynamicMerkleTree::insert`, and wrote: "The spec says removal 'adds that leaf index to the list of unused leaves' and adding calls `ledger.add(output_note_id)`; neither sentence specifies FIFO, LIFO, lowest-index allocation, or preference over never-used leaves. The implementation recycles indices as required. Root differences between two policies demonstrate why a future conformance specification could define a policy, but do not establish that this code contradicts the supplied requirements."
- Disposition: both passes agree the implementation recycles freed indices lowest-first, that the section states no allocation policy, and that the root depends on the policy. The dispute is whether an unpinned consensus-relevant choice is a reportable spec gap under `undefined-behaviour` (first pass) or outside the audit's scope because the code contradicts nothing (second pass).
