### contradicts-spec (proven violations)

#### Finding 1 (F-c30dcb20) — DeclarationMessage::id hashes the ASCII bytes "BN" as the service component of declaration_id instead of the canonical one-byte discriminant 0x00 — **confirmed**, medium severity, medium confidence

The specification says `ServiceType.BN = 0` and "the one-byte discriminant is the canonical encoding", and the SDP LIP's Declaration Storage defines `declaration_id = Hash(service||provider_id||zk_id||locators)` with each component in its canonical encoding. `DeclarationMessage::id` instead feeds the two ASCII bytes 0x42 0x4E as `service`, while the payload codec writes 0x00 for the same field. The other three preimage components are canonical, so this is the only divergence, and every declaration id this ledger derives differs from the spec's. SDP_DECLARE validation step 2 and the SDP_WITHDRAW / SDP_ACTIVE lookups all key on that id. The finding does not show fund loss: this node is internally consistent, and the impact is interoperability with any party that derives ids per the specification.

- Locations: `core/src/sdp/mod.rs:542-549` (the `"BN"` string hashed as the service component), `core/src/sdp/mod.rs:310-340` (the canonical `0x00` payload encoding of ServiceType).
- Repro: `cargo nextest run --locked -p logos-blockchain-core --all-features --no-fail-fast --test 20261023T045453-a1df9b_1` → observed: `assertion left == right failed: declaration_id must hash service as its canonical one-byte discriminant [00]; the computed id 0x019e6a82... equals the hash over the ASCII string "BN" instead: true`, exit 100. The control `service_type_bn_is_encoded_as_the_single_byte_zero` passes.
- Second pass: confirmed — re-ran the target (actual 019e6a82... vs expected 7fb647c0...), read `DeclarationMessage::id` and the ServiceType encoder, and fetched the SDP LIP's Declaration Storage section, which requires the service as its one-byte discriminant. "This is a real hashing divergence, not merely a payload representation difference."
- Fix: replace the `"BN"` / `service.as_bytes()` pair with `hasher.update(self.service_type.encode())`. Every declaration id changes, genesis included, so the change needs a coordinated upgrade or genesis regeneration. The proof test passes after the change.

#### Finding 3 (F-a5cd7a5b) — Locator::try_from rejects a well-formed multiaddr with an unspecified IPv4/IPv6 host, which Locator.validate accepts — **confirmed**, medium severity, medium confidence

`Locator.validate()` has exactly two conditions, `len(self) <= 329` and `validate_multiaddr(self)`. `impl TryFrom<Multiaddr> for Locator` also rejects any `Ip4`/`Ip6` component that is unspecified and any `/p2p` component, and every decode path (binary, serde, FromStr) goes through it. The second pass established from the SDP LIP's Locators section that a locator "must not contain the node identity (peer_id)", so the `/p2p` rejection is correct and the Mantle example's bare `/ip4/203.0.113.10/tcp/4001/p2p` is itself malformed. What remains confirmed is the unspecified-host rejection: an SDP_DECLARE with `/ip4/0.0.0.0/tcp/4001` passes the specification's validate but is undecodable here, so a block carrying it is rejected by this node and accepted by a spec-conformant validator. The doc comment on the type also misstates the policy (it claims loopback, multicast, documentation and link-local rejection; those are accepted). Scope is input acceptance only.

- Locations: `core/src/sdp/mod.rs:188-218` (try_from with the unspecified-host and peer-id rejections), `core/src/sdp/mod.rs:123-130` (doc comment misstating the rule), `core/src/sdp/mod.rs:271-283` (decoder mapping the error to `Invalid locator bytes`).
- Repro: `cargo nextest run --locked -p logos-blockchain-core --all-features --no-fail-fast --test 20261023T045453-a1df9b_3` → observed: `locator_with_an_unspecified_host_is_valid` fails with `/ip4/0.0.0.0/tcp/4001 passes Locator.validate() and must decode as a locator: Err(InvalidValue { type_name: logos_blockchain_core::sdp::Locator, message: Invalid locator bytes })`, exit 100. The `locator_with_a_peer_id_component_is_valid` test also fails, but its assertion is wrong per the SDP LIP. The byte-bound control passes.
- Second pass: confirmed (unspecified-host subclaim only) — ran target 3, read try_from and the decoder, and fetched the Locators section: "rejecting Protocol::P2p is correct, and the example's bare /p2p is itself malformed. That section does not add an unspecified-host restriction."
- Fix: drop the `is_unspecified()` rejections from try_from (moving any such policy to the node code that builds declarations), or add the rule to the specification; correct the doc comment and the Mantle example either way. Remove the peer-id assertion from the proof test; the unspecified-host test then passes once such locators decode.

#### Finding 5 (F-8e9ee2fa) — MinStake records `timestamp: BlockNumber` where the specification's MinStake records `epoch: EpochNumber` — **confirmed**, info severity, high confidence

The specification defines `class MinStake: stake_threshold: int; epoch: EpochNumber`, and the SDP LIP's Minimum Stake section defines the field as the epoch at which the threshold was set. The code's `MinStake` is `{ threshold: StakeThreshold, timestamp: BlockNumber }`, a u64 block number, while the neighbouring `ServiceParameters` correctly carries `epoch: Epoch`. No Rust code reads the field; it is set as `timestamp: 0` in deployment YAML. The finding establishes schema drift only, with no current validation or execution consumer.

#### Finding 2 (F-bbcbb4be) — WithdrawMessage encodes declaration||nonce||service_note_id while the Mantle section lists the fields as declaration, service_note_id, nonce — **disputed**, medium severity, medium confidence

The Mantle section writes `class WithdrawMessage: declaration: DeclarationID; service_note_id: NoteId; nonce: int`. - Locations: `core/src/sdp/mod.rs:589-594` (WithdrawMessage field order with `#[derive(BinaryCodec)]`), `core/src/mantle/fixtures/ops/op_values.rs:134` (fixture pinning the order).

- Second pass: rejected — "both assertions fail, but they assert an incorrect wire order. The supplied sentence ... describes logical fields, not a byte grammar. ### undefined-behaviour (proven violations)

#### Finding 4 (F-22d9e2cd) — Locators is a NonEmptyBoundedOrderedSet, so a payload whose locator list repeats an entry fails to decode although the specification's list has only the bound 1 <= len <= 8 — **confirmed**, low severity, medium confidence

The specification types the field as `locators: list[Locator]`, and validation step 3 asserts only `1 <= len(locators) <= 8`; neither it nor the SDP LIP's Declaration Message and Locators sections require distinct entries. The code types the field as `NonEmptyBoundedOrderedSet<Locator, 8>`, whose decoder rejects a repeated element instead of dropping it, so a declaration listing the same locator twice never reaches validation. The specification is silent on duplicates and the code picks rejection: a consensus-visible deviation on such payloads, but a narrow one. Duplicate locators confer no additional service rights.

- Locations: `core/src/sdp/mod.rs:526-527` (the `Locators` alias), `utils/src/bounded/ordered_set.rs:40-48` (documented rejection of repeated elements on every construction path).
- Repro: `cargo nextest run --locked -p logos-blockchain-core --all-features --no-fail-fast --test 20261023T045453-a1df9b_4` → observed: `a declaration whose locator list has 2 entries satisfies 1 <= len(locators) <= 8 and must decode with both entries: Err(DuplicateItem { type_name: ...Bounded<OrderedSet<Locator>, 1, 8>, index: 1 })`, exit 100. The control showing the payload builder is byte-identical to the codec for distinct locators passes.
- Second pass: confirmed — ran target 4, read the Locators alias, and checked the linked Declaration Message and Locators sections: "they specify a list, length bounds and canonical framing, without a distinctness rule. This is a narrow input-acceptance divergence."
- Fix: type `locators` as a bounded list (e.g. `BoundedVec<Locator, 1, 8>`) so every list the specification admits decodes, or keep the set and add "locators must be pairwise distinct" to the specification. The proof test passes once a two-entry list with a repeated locator decodes.

### spec-drift (proven violation: finding 6; documentation drift: findings 7 and 8)

#### Finding 6 (F-1a188eba) — ActiveMessage.metadata is encoded as a 0x01 service tag plus a fixed-layout Blend proof with no length envelope, where the specification carries opaque bytes and the canonical encoding specifies `Metadata = UINT32 *BYTE` — **confirmed**, low severity, medium confidence

The specification's Active payload is `metadata: bytes # a service-specific node activeness metadata`, and the canonical encoding document gives `SDPActive = DeclarationId Nonce Metadata`, `Metadata = UINT32 *BYTE`. The code decodes a typed `ActivityMetadata` directly in the Mantle payload codec: one tag byte (`ACTIVE_METADATA_BLEND_TYPE = 1`) followed by the fixed Blend ActivityProof layout, with no byte-count envelope. So even valid Blend metadata lacks the required UINT32 envelope, a spec encoder's length prefix is misread as the service tag, and metadata the service logic would reject makes the transaction undecodable instead of an invalid Operation as the Execution text says. Filed as spec-drift because the typed metadata reads as the current design and the fix may be partly documentary; the framing divergence itself is concrete.

- Locations: `core/src/sdp/mod.rs:596-664` (ActiveMessage, ActivityMetadata and its tag-plus-proof codec), `core/src/sdp/blend.rs:35-74` (fixed proof layout without a length prefix).
- Repro: `cargo nextest run --locked -p logos-blockchain-core --all-features --no-fail-fast --test 20261023T045453-a1df9b_6` → observed: every framing of the example metadata is rejected, unprefixed with `UnknownDiscriminant { type_name: logos_blockchain_core::sdp::ActivityMetadata, discriminant: 76 }` and each length-prefixed form with `UnknownDiscriminant { ..., discriminant: 29 }`, exit 100.
- Second pass: confirmed — ran target 6, read the codec and blend.rs, and fetched the canonical encoding: "even valid Blend metadata lacks the required UINT32 byte-count envelope. Narrow the remedy to implementing the specified opaque-byte framing and parsing service metadata appropriately; changing the internal Rust type alone is unnecessary."
- Fix: encode `metadata` on the wire as length then bytes, and parse the tagged Blend proof from those bytes in the service-specific activity logic so malformed metadata invalidates the Operation. Update SDP_ACTIVE fixtures and replace the example's free-text metadata. The u32-prefixed framing in the proof test then decodes.

#### Finding 8 (F-7e5a598d) — The SDP_WITHDRAW worked example spends the service note in the withdraw transaction, but the ledger keeps it locked until the first block of epoch withdraw_at + 1 as SDP Epoch Finalization requires — **confirmed**, low severity, high confidence, prose-only

The example's TRANSFER therefore fails its input check with `InputsError::ServiceNote`. The fix is to the document; collateral must not be unlocked at withdrawal execution.

- Locations: `ledger/src/mantle/sdp/mod.rs:547-571` (apply_withdrawn_msg leaves the note locked), `ledger/src/mantle/sdp/mod.rs:226-265` (unlock only at the epoch transition), `core/src/mantle/ledger.rs:349-358` (spend check rejecting locked notes, outside unit).
