### contradicts-spec (proven violations)

#### Finding 1 (F-1abd415c) — `DeclarationMessage::id()` hashes the ASCII string `"BN"` as `service` instead of the one-byte ServiceType discriminant, so every declaration_id differs from the Appendix — **confirmed**, high severity, high confidence

The Appendix defines `declaration_id = Hash(service || provider_id || zk_id || locators)` (BLAKE2b-256, no DST) where `service` is the one-byte ServiceType discriminant, and gives the vector preimage `0x00 || provider_id || zk_id || locators` → `0x7fb647c069bade94e06685b0825299d220e7cc14752cfc474773b6c4040e37b5`. `DeclarationMessage::id()` in `core/src/sdp/mod.rs` maps `ServiceType::BlendNetwork` to the string `"BN"` and feeds `service.as_bytes()` (`0x42 0x4e`) to the hasher. Everything else in the preimage matches the spec (field order, provider_id bytes, canonical 32-byte little-endian zk_id, the Locators production with u8 count and 2-byte LE lengths, service_note_id excluded, Blake2b with 32-byte output), so the service prefix is the only divergence, and it changes every declaration id. The code is internally inconsistent: ServiceType's own wire encoding (`BinaryEncode`, and the SDP_DECLARE payload) is the discriminant `0x00`; only the id uses `"BN"`. declaration_id keys the ledger's declarations and is what SDP_WITHDRAW and SDP_ACTIVE reference, so a spec-conformant implementation computes different ids for the same declarations and cannot agree with this node on SDP state. The finding establishes the hash divergence with a unit test; the end state (two implementations disagreeing on SDP state) needs a second implementation and is not demonstrated. No fund loss is shown.

- Locations: `core/src/sdp/mod.rs:540-557` (`DeclarationMessage::id()`; `:542-549` is `let service = match self.service_type { ServiceType::BlendNetwork => "BN" }; hasher.update(service.as_bytes());`).
- Repro: `cargo nextest run --build-jobs 4 --locked -p logos-blockchain-core --all-features --no-fail-fast --test 20261023T062355-5c07bf-1 declaration_id_matches_the_appendix_vector` → observed: `assertion 'left == right' failed: DeclarationMessage::id() does not reproduce the Appendix declaration_id ... left: "019e6a82692d5533fc162b137c11fd2ad1e2c4f2bc1e728237e00572e7331526" right: "7fb647c069bade94e06685b0825299d220e7cc14752cfc474773b6c4040e37b5"`. The companion test `declaration_fields_are_the_vector_fields` passes: with the code's own encoders, service encodes to `00`, the other fields to the vector's bytes, Blake2b-256 of their concatenation is `7fb647c0…`, and `Op::SDPDeclare` of the declaration encodes to the Appendix SDP_DECLARE payload. Independent check with Python `hashlib.blake2b(digest_size=32)`: the Appendix preimage hashes to `7fb647c0…`, and `b"BN" + preimage[1:]` hashes to `019e6a82…`.
- Second pass: confirmed — ran the four proof tests (9 loaded, 1 passed, 8 failed with assertion or decoding failures, not setup failures); `declaration_id_matches_the_appendix_vector` failed with actual `019e6a82…` versus required `7fb647c0…`. Independently read `DeclarationMessage::id` at `core/src/sdp/mod.rs:540-557`: it hashes `service.as_bytes()` after mapping BlendNetwork to `"BN"`. The Appendix explicitly requires the one-byte ServiceType discriminant, `00`, so these two ASCII bytes violate the preimage requirement. It also resolved the ref: HEAD is proof commit `a842c274`, whose parent and the resolved 0.3.0 commit are `f76be2dd`; the supplied `1da2d9d6` is the annotated tag object, not the peeled commit.
- Merge-pass adjudication: reran the proof on the proof branch; same failure, same two hashes.
- History: the `"BN"` string has been in `id()` since 97b411ed (2026-01-20); later fixes (6e2e4a91 canonical zk_id, db69ba22 length-prefixed locators, 2026-07-30) brought the other three fields to the spec form and left the service prefix. The comment at `mod.rs:546-548` cites the SDP formula but not the one-byte encoding.
- Fix: in `DeclarationMessage::id()` hash the ServiceType discriminant byte (`hasher.update([*<ServiceType as AsRef<u8>>::as_ref(&self.service_type)])`, or `self.service_type.encode()`) instead of the `"BN"` string. This changes every declaration id, so genesis declarations, the testnet genesis artifacts and any persisted state keyed by DeclarationId must be regenerated together. Keep the Appendix vector as a permanent unit test next to `id()`; `core/tests/20261023T062355-5c07bf-1` fails today and passes after the change.

#### Finding 2 (F-177899a9) — The SDP_ACTIVE encoding omits the Blend activity-proof version byte (`0x01`) the Appendix carries after the metadata type, so the spec SDP_ACTIVE payload and the "one of each operation" transaction are rejected and their op_id / tx hash differ — **confirmed**, high severity, high confidence

The Appendix SDP_ACTIVE payload is 270 bytes: `declaration_id(32) || nonce(8) || 0x01 || 0x01 || epoch(4) || signing_key(32) || proof_of_quota(160) || proof_of_selection(32)`, op_id `0x76afa55f…`. The code (`ActivityMetadata` in `core/src/sdp/mod.rs` writes the metadata type `0x01`, then `ActivityProof` in `core/src/sdp/blend.rs` writes epoch, key, PoQ, PoS) produces 269 bytes with a single `0x01`, op_id `0xc4a2a639…`. Decoding the Appendix payload with `Op::decode` fails: the code takes `01 0a 00 00` as the epoch and starts the signing key one byte early, which is not a valid Ed25519 point, so the Appendix "one of each operation" transaction cannot be decoded either and its hash `0x11e60138…` cannot be reproduced. With that single byte removed the code decodes all ten operations and round-trips them, so this byte is the only divergence among the Appendix operation vectors (the other nine op_ids and the empty-transaction hash match). The missing byte is the `BLEND_ACTIVE_METADATA_VERSION_BYTE` (`0x01`) the code itself wrote after `ACTIVE_METADATA_BLEND_TYPE` until commit 6262a8a4 (2026-09-30, "feat(eras): remove variant tags and move block slot first"), which deleted it and regenerated the code's own fixtures; the Appendix (2026-10-08 snapshot) still has it. Because the removal was deliberate, this may be spec drift, in which case the fix is to regenerate the spec's grammar and vectors; against the specification as published the code is wrong. The finding establishes the encoding divergence with unit tests; the end state (a spec-conformant node and this node disagreeing on an SDP_ACTIVE transaction) needs a second implementation and is not demonstrated.
