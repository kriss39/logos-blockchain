### contradicts-spec (proven violation)

#### Finding 1 (F-f3f66fd4) — TransferOp::balance sums inputs and outputs in u64 before widening to i128, rejecting TRANSFERs whose note-by-note checked_int128 balance is valid — **confirmed**, low severity, high confidence

The specification (Mantle Transaction > Validation step 2, and Arithmetic) defines a TRANSFER's effect on the transaction balance note by note in a signed 128-bit accumulator: `for inp in op.inputs: tx_balance = checked_int128(tx_balance + get_value_from_note_id(inp))`, then `for out in op.outputs: tx_balance = checked_int128(tx_balance - out.value)`. There is no per-TRANSFER u64 sum, and with at most 255 u64 notes per side the i128 accumulator cannot overflow. `TransferOp::balance` instead adds all input values as u64 through `Inputs::amount` and all output values as u64 through `Outputs::amount`, and only then widens to i128. A TRANSFER whose inputs, or whose outputs, add up past u64::MAX is rejected with `InputsOverflow` or `OutputsOverflow` although every note is a valid TokenValue, the i128 balance stays in range and the transaction pays its fee with a uint64 tip. The shipped default, testnet, devnet and standalone genesis give the faucet key one note of u64::MAX beside 121 notes of 8e12, so any TRANSFER spending the faucet note with another note hits the input overflow. A spec-conformant implementation accepts such a transaction while this node rejects any block carrying it. The finding does not establish fund loss or unauthorised spend; it is reachable on the shipped genesis only by the faucet key holder and is unreachable on a chain whose total supply stays below 2^64.

- Locations: `core/src/mantle/ops/transfer.rs:58-69` (`TransferOp::balance`, the u64 sums then the i128 widening); `core/src/mantle/ledger.rs:377-388` (`Inputs::amount`, u64 checked_add → `InputsOverflow`); `core/src/mantle/ledger.rs:182-190` (`Outputs::amount`, u64 checked_add → `OutputsOverflow`); `ledger/src/cryptarchia/mod.rs:579-581` and `ledger/src/lib.rs:876-886` (where the ledger applies and accumulates it).
- Repro: `cargo nextest run --build-jobs 4 --locked -p logos-blockchain-ledger --all-features --test transfer_balance_20261023T055257_ab1c46_1` → observed: "Summary: 3 tests run: 0 passed, 3 failed"; `main.rs:155`: "assertion `left == right` failed: the TRANSFER adds 8000000000000 to the spec's i128 tx_balance; left: Err(Inputs(InputsOverflow)); right: Ok(8000000000000)"; `main.rs:189`: "the spec accepts this TRANSFER: its balance fits the i128 accumulator: Mantle(Transfer(Inputs(InputsOverflow)))"; `main.rs:230`: "the spec accepts this TRANSFER: its outputs are valid notes and i128 holds 2^64: Mantle(Transfer(Outputs(OutputsOverflow)))". The proof uses only public APIs with real ZkSignatures and the shipped faucet key configuration; with `TransferOp::balance` temporarily rewritten to accumulate note by note in checked i128 (then restored byte for byte) all three tests pass, so they fail only on this divergence.
- Second pass: confirmed — ran the same command independently (exit 100, the same three assertions failing at `main.rs:155`, `:189`, `:230`); read `TransferOp::balance` and both `amount` helpers and confirmed they checked-add in u64 before widening; read the note-by-note `checked_int128` rule at spec lines 200–208 and confirmed the TRANSFER section introduces no aggregate u64 bound; ran the ten existing core TRANSFER tests, all green; diffed the six audited files against the brief's ref with no difference.
- Merge-pass adjudication: not applicable; the first pass raised this finding and the harness takes the second pass's verdict. The merge pass checked that the proof artifact and its `[[test]]` registration are on the proof branch and that `transfer.rs:58-69` reads as described.
- Disposition: not applicable; both passes agree.
- Fix: in `TransferOp::balance`, iterate `self.inputs`, look each note up (`InexistingNote` if absent) and `checked_add(i128::from(note.value))`; then iterate `self.outputs` and `checked_sub(i128::from(out.value))`; map a failed step to `TransferError::BalanceOverflow`. Do not route the balance through the u64 `amount` helpers or merely widen them. Per-note bounds stay as they are. The three proof tests then pass. Related and outside this unit: compute the tip at `ledger/src/lib.rs:515` with `Value::try_from(balance - fee)` and reject on failure instead of `balance as Value`.
