### Contradicts-spec (proven violation)

#### Finding 1 (F-82904c5e) — LEADER_CLAIM mints a standalone UTXO instead of crediting the Mantle transaction's balance — **confirmed**, medium severity, high confidence

The spec's "Claiming the reward" section says the LEADER_CLAIM Operation "increases the balance of a Mantle Transaction by the leader reward amount, letting the leader move the funds as desired through the Ledger transaction or another Operation", and stresses that "a leader may use their funds directly, getting their reward and using them atomically"; Validation step 3 repeats "Increase the balance of the Mantle Transaction by the share amount". The implementation does neither. `LeaderClaimOp::execute` inserts a fresh UTXO built from a `pk` field the operation carries (a field this LIP's operation does not have) into the UTXO set, and the ledger's per-operation application leaves the transaction's running `balance` untouched — only Transfer operations contribute to it. Because the transaction-level check rejects any transaction whose balance does not cover its gas (`LedgerError::InsufficientBalance`), a transaction whose only operation is a perfectly valid LEADER_CLAIM is rejected: the reward can never pay the claiming transaction's fees or fund a transfer in the same transaction, and a leader with no other spendable funds cannot claim at all — the atomic-use design the spec explicitly promises. What the finding does not establish: no funds are lost — the share is still delivered, as a separate pk-addressed UTXO — and the finding does not settle which document is normative (the implementation looks deliberate and may follow the adjacent Mantle specification's LEADER_CLAIM section, audited by another brief; if that section is normative, this reclassifies as spec-drift in the LIP's text).

- Locations: `core/src/mantle/ops/leader_claim.rs:283-311` (`execute()` inserts `operation.utxo(context.reward_amount)` into `context.utxos` and subtracts the share from `claimable_rewards`; `LeaderClaimExecutionContext` at lines 200-206 has no balance field), `core/src/mantle/ops/leader_claim.rs:62-79` (the op's `pk` field, not in this LIP's operation), `ledger/src/lib.rs:856-874` (the `SignedOp::LeaderClaim` arm of `try_apply_op` never touches the `balance` accumulator; contrast the `Transfer` arm at `lib.rs:876-886`), `ledger/src/lib.rs:492-515` (`try_apply_transaction` rejects on `balance` < gas and computes the fee tip from `balance` alone).
- Repro: `cargo test --locked -p logos-blockchain-ledger --all-features --lib finding_4956ec_1` → observed: `panicked at ledger/src/finding_4956ec_1.rs:107:5: spec: the LEADER_CLAIM Operation increases the balance of the Mantle Transaction by the leader reward amount (1000000), which covers the transaction's gas, so a claim-only transaction must be accepted; the implementation never credits the balance and rejected it with: Some(InsufficientBalance)` — `test result: FAILED. 0 passed; 1 failed`. The test builds a claimable voucher (snapshotted at the epoch-1 transition, pool = 1,000,000, one unclaimed voucher so share = 1,000,000), generates a real Groth16 proof of claim over the transaction's hash with the prebuilt PoC circuit, and applies a claim-only transaction via the public `LedgerState::try_apply_transaction`; the claim preverifies and verifies, execution mints the UTXO, yet the transaction is rejected.
- Second pass: confirmed — it independently ran the same command (one test ran and failed at `finding_4956ec_1.rs:107` with `Some(InsufficientBalance)`, exit 101), read the proving code end to end, and independently traced the three code sites; it also resolved the audited release commit (`f76be2dde…`, with the brief's `1da2d9d6…` being the annotated tag object peeling to it), verified the proof branch changes nothing but the test, and scanned all unit files for further divergences, finding none it could support.
- Fix: decide which document is normative. If this LIP is: extend `LeaderClaimExecutionContext`/`execute` to return the share as a balance credit, add it to the transaction's `balance` in the `SignedOp::LeaderClaim` arm of `try_apply_op` (mirroring the Transfer arm), and drop the pk/UTXO minting (or keep it as the explicit output of the credited balance). If the Mantle spec's UTXO form is normative: update this LIP's "Claiming the reward" and "Validation" sections to describe the pk-addressed UTXO payout and remove the atomic-use claim. Gate test: `ledger/src/finding_4956ec_1.rs` (`leader_claim_credits_the_transaction_balance_with_the_share`) fails on the current code and passes once a claim-only transaction's reward covers its gas.

No findings were raised in the wrong-default, off-by-requirement, missing-requirement, undefined-behaviour or spec-drift classes.
